# Home Session planning and persistence

The planner proposes due chores for a 5, 15 or 30 minute session. A task is due when its last completion date plus its repeat interval is on or before the current local calendar date. A task with no completion date is also due. The filters call tasks due today or earlier **overdue**, tasks due in one or two days **soon**, and the remainder **fresh**.

The priority score for a task with history is `floor(elapsed calendar days × 100 / interval days)`, plus 0 for low priority, 25 for normal and 50 for high. A task with no history uses a finite baseline of 150 plus that priority bonus. Known severe overdue age can therefore outrank a new task. Equal scores use overdue days, then the stable task ID, as tie breakers.

Tasks are considered in that order. A task is selected when its complete estimated duration fits the remaining budget; otherwise the planner continues to consider the next task. This is a greedy priority-first selection, not an optimal knapsack search or a guarantee that every minute will be filled. Tasks longer than the whole budget are reported separately as `TOO_LONG`; other tasks that do not fit are reported as `BUDGET`. Every selected task carries its reason: no completion recorded, due today, or the number of overdue days. An empty proposal distinguishes no due chores from due chores that cannot fit. Neither case creates a session.

`planSession` is read-only. `startSession` saves the selected list without changing completion dates or history. Only an explicit `markDone` creates a journal event and updates a task's last completion date. Repeated marking is idempotent. `undoDone` removes that event and restores the previous date when the event still owns the date; a manual date edit is preserved. Completed journal titles and room names are snapshots.

Pending session items reflect edits to their task or room. Items that become fresh or exceed the remaining budget move to `TASK_UPDATED` exclusions. Completed items keep their original time and journal snapshot. Deleting a pending task removes it from the session; deleting a completed task preserves its journal event and permits undo during that session. Deleting a room moves its tasks to the unassigned group. Finishing or cancelling keeps explicit completions and leaves unchecked tasks unchanged.

The versioned JSON stores rooms, all editable task fields, completion events, and the active session with individual completion IDs. ISO dates are independent of the display language. Completion timestamps and local dates derive from the same captured instant. The default local zone is read for each operation. Private Android `AtomicFile` storage commits the whole state before publishing it to the UI. Failed writes leave the in-memory state unchanged; invalid, inconsistent or unsupported JSON raises a read error instead of resetting user data. Resume and undo survive repository recreation.
